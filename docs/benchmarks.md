# 數據機優化的模擬數據（A/B 比較）

> 所有數字都由 `npm run bench -- <區段>` 實際跑出（`bench/run.ts`），亂數種子固定，可重現。
> 每項優化都是 `RxOptions` 中可開關的設定；**有明確改善才設為預設**（`DEFAULT_OPTIONS`），沒改善的也保留紀錄。
> 「baseline」是 PoC `modem.js` 的忠實 TypeScript 移植（`BASELINE_OPTIONS`，全部優化關閉），測試 3、4 同時驗證它仍達到門檻。

## 0. 方法

**通道模擬**（`bench/channel.ts`，移植自 PoC 的 `channel()`）：
- 發送端 48 kHz、振幅 0.6、8 bytes 隨機 payload；接收端 44.1 kHz（線性內插重新取樣，PoC 相同做法），另測 48 kHz。
- 隨機前置靜音 0.3～1.3 秒；直達聲＋300 個稀疏反射（指數衰減）；白噪音；300 Hz 低頻干擾（振幅 0.3）。
- 新增選項：**高頻衰減**（兩級 Butterworth 低通 fc = 19 kHz、Q = 0.707）、**都卜勒**（以 τ(t) = ∫(1 + v(t)/343)dt 重新取樣，支援時變速度）、**窄頻干擾**（設備的持續性高頻嘯叫）、**移動多路徑衰落**（每條反射路徑各自的都卜勒，見 3.6 節）。
- 「重送合併」的兩次傳送使用**獨立的通道實現**（獨立的反射與噪音）：20 kHz 的波長只有 1.7 cm，手持手機在兩次傳送之間（中間有 5～10 秒的語音廣播）只要移動幾毫米，多路徑的相位關係就完全不同。

**一個重要的發現**：以接收端實際的「目標頻道功率／其他頻道中位數」量測，各情境每個符號的 SNR 中位數為
安靜 43.9 dB、強 16.6 dB、高頻衰減＋安靜 33.1 dB、高頻衰減＋中等 13.6 dB（10% 分位 9.3 dB）、**高頻衰減＋強 6.9 dB（10% 分位 −0.4 dB）**。
也就是說，「高頻衰減＋強噪音」下有一成的符號訊號比噪音還弱，16 選 1 的判定在物理上就無法可靠——這與需求文件「兩種模式都是 0/30、只能靠提高音量或換喇叭」的結論一致。
另外，48 → 44.1 kHz 的線性內插本身會讓 20 kHz 衰減約 5 dB（sinc² 響應），這是 44.1 kHz 手機比 48 kHz 手機吃虧的原因之一。

測試 5-1（`tests/doppler.*.test.ts`）：手動頻段兩種模式、自動偵測模式，所有速度與走路情境在安靜 ≥ 95%、中等 ≥ 85% 全部通過（共 48 項）。

**做法與原理**（`src/modem/receiver.ts`、`doppler.ts`）
1. **問題**：r(t) = s(αt)，α = 1 + v/343。19.5～20.35 kHz 在 1.5 m/s 時偏移 85～89 Hz，超過 50 Hz 的頻道間距；baseline 以固定頻率做 Goertzel，0.5 m/s 就完全收不到（重現了需求文件的實測）。
2. **偵測：共用 FFT＋頻偏搜尋**。每個 hop 對偵測窗做一次 FFT（補零 1.5 倍，bin 約 10.8～11.7 Hz），在 ±150 Hz 內以 bin 為步長（27 個頻偏）計算前導碼分數，取最大者。符號長度相同的 4 個頻段**共用同一份 FFT**（`SpectrumCache`），所以 8 組候選設定只需要 2 組 FFT。
3. **同步**：在前導碼上先搜尋時間（±N/4、1 ms），再在 ±18 Hz 內以 2 Hz 步長精細估計頻偏，再微調一次時間。頻偏換算成 α 後，所有頻道頻率乘 α、符號長度除以 α（同時處理 2.4 秒封包約 10 ms 的時間伸縮）。
4. **決策導向追蹤**：每判定一個信心值（最大／第二大功率）≥ 2.5 的符號，就在判定頻道 ±10 Hz 各算一次 Goertzel，以對數功率的三點拋物線內插估計實際頻率，以增益 0.45 更新 α。速度在一則廣播中緩慢變化時（走走停停、轉身），沒有追蹤只有 20%，有追蹤 100%。
5. **計算量**：見第 5 節，含頻偏搜尋的自動偵測比 baseline 還快。

**評估過但未採用**：上升＋下降啁啾（chirp）前導碼。它能用匹配濾波同時估計時間與頻偏，但會改變封包格式、與 PoC 不相容，而且我們的 FFT 頻偏搜尋已在所有速度達到 97～100%，因此沒有實作。

## 3. 吵雜環境（3.5.2）

### 3.1 低 SNR 偵測（新增）

**問題**：PoC 的偵測分數是「同步音占 18 頻道總功率的比例」，門檻 0.3。白噪音下，18 個頻道各分到一份噪音，所以每個頻道的 SNR 至少要約 7 dB 才觸發；弱訊號時，資料其實解得出來，卻連前導碼都偵測不到（「高頻衰減＋強」與「極強」的失敗中，超過一半是「沒有偵測到」）。

**做法**：以「同步音功率 ÷ 參考值」取代比例，參考值 = 18 個頻道去掉最大兩個後的平均（背景噪音估計）＋ 0.5 ×（整個搜尋頻帶最強 bin − 目標功率）。後一項確保目標必須是頻帶中的主導者——開發中發現，若只除以噪音，安靜環境下噪音底極低，頻偏搜尋時相鄰頻道落在強音主瓣內的洩漏也會變成「高 SNR」，導致提早兩個符號觸發（安靜情境掉到 0%）。倍數 z 以 z / (z + 7) 映射到 0～1，使 z = 3 時恰為原本的門檻 0.3；觸發後仍以原本的比例分數找峰值（比例分數峰值尖銳，SNR 分數在強訊號時會飽和成平台）。

**結果**：「極強」7% → 17%，其他情境不變；60 秒純噪音誤報 0 次（測試 4）。**採用**。

### 3.2 軟判決＋抹除解碼

**做法**：每個符號的信心值 = 最大功率／第二大功率；每個位元組取兩個 nibble 中較低者。RS 錯誤解碼失敗時，依序把信心最低的 2 個、4 個位元組標為抹除再解（2e + f ≤ nsym − 2）。header（len、~len）原本沒有任何保護，錯一個符號整則就丟掉；軟判決時改在所有合法長度中找「只差 1 個符號」者，以期望頻道的對數似然取最可能的長度。

**為什麼保留 2 個位元組的偵錯餘量**：nsym = 6 時若用滿 6 個抹除，就沒有任何多餘的 syndrome 可以檢查，任何雜訊都會被「修」成一個合法碼字。我們估算並在測試中驗證：保留 2 個餘量時，錯誤接受機率約 10⁻⁵ 以下；所有基準與測試都要求「錯誤訊息數 = 0」。

**結果**：「強」90% → 97%、「高頻衰減＋中等（穩定）」83% → 100%、「窄頻干擾」67% → 80%，無錯誤訊息。**採用**。

### 3.3 重送合併

站務端預設送兩次相同 seq 的訊號（中間是語音廣播）。兩次都無法單獨解碼時，把兩次對應符號的 16 頻道功率（各自先正規化成總和 1）相加後再判定。

| 情境 | 單次接收 | 送兩次、不合併 | 送兩次＋合併 | 提升（相對單次） |
|---|---|---|---|---|
| 強（噪音 0.05、回音 0.8 s） | 95%（38/40） | 98%（39/40） | 100%（40/40） | 5 個百分點 |
| 極強（噪音 0.1、回音 1.2 s） | 28%（11/40） | 40%（16/40） | 70%（28/40） | 43 個百分點 |
| 高頻衰減＋中等 | 100%（40/40） | 100%（40/40） | 100%（40/40） | 0 個百分點 |
| 高頻衰減＋強 | 0%（0/40） | 0%（0/40） | 0%（0/40） | 0 個百分點 |

- 每格 40 次，標準模式；兩次傳送間使用獨立的通道實現。
- 配對：失敗的封包讀不到 seq，所以兩次 header 都正確時要求 len 相同；任一次 header 壞掉時，把兩次 header 的符號功率相加後再判定長度。前導碼品質足夠的失敗封包會在背景繼續解調到最大長度，供之後的合併使用；品質不足者（多半是噪音假觸發）不進暫存區，只在能和暫存的好封包配對時才解調。暫存區只保留時間窗（20 秒）內品質最好的 4 個。長度是猜出來的時候，RS 保留 2 個偵錯餘量。
- 測試 5-2（`tests/noise.test.ts`）：「極強」情境要求合併比單次接收提高 ≥ 10 個百分點且比「送兩次、不合併」更好；「強」情境單次已達 9 成以上，改為要求合併後 ≥ 95%。
- 兩次傳送之間有另一則廣播（例如另一個月台）解碼成功時，暫存的失敗封包只在「與成功封包的符號一半以上相同」時才移除，所以不影響合併（`tests/regressions.test.ts`：中間穿插 B 與中間靜音的合併結果相同）。
- 需求文件原本要求在「強噪音」情境驗證；在 PoC 的通道模型中，若兩次傳送共用同一組反射，單次就已經有 93%，不可能再提高 10 個百分點。使用獨立通道實現（理由見第 0 節）後，合併在「極強」情境 28% → 70%（+43 個百分點）；「強」情境單次已達 95%，合併補到 100%。**採用（不可砍）**。

### 3.4 頻道白化

| 版本（其他優化全開；開發過程的紀錄，種子 9000～9029） | 中等＋窄頻干擾（標準） | 說明 |
|---|---|---|
| 不白化 | 77%（23/30） | |
| 白化 v1：除以「沒被選中時的功率中位數」 | 50%～67% | 干擾比訊號強時，干擾頻道幾乎每次都「被選中」，噪音估計崩潰；**變差，捨棄** |
| 白化 v2：除以低百分位數背景 | 30%～47% | 訊號剛好落在干擾頻道的符號被壓得太低；**變差，捨棄** |
| 偵測端白化（每個 FFT bin 的 CFAR 背景） | 17%～30% | 與 3.1 的「主導者」條件衝突：強音旁邊的 bin 白化後反而比中心更大；**變差，捨棄** |
| **白化 v3：扣除各頻道高出噪音底的背景（25% 分位數）** | **97%（29/30）** | 對持續性窄頻干擾最有效；**採用** |

v3 的原理：持續性干擾在每個符號都存在，所以各頻道功率的 25% 分位數 ≈ 噪音底＋干擾；資料音只在約 1/16 的符號出現，幾乎不影響分位數。扣除「高出噪音底的部分」後，干擾頻道回到和其他頻道一樣的水準，而訊號剛好落在干擾頻道時，因為訊號＋干擾 ≫ 干擾，仍然判得出來。無干擾的情境中，各頻道背景相同、扣除量為 0，不影響結果（第 1 節所有情境都不低於 baseline）。

### 3.5 迴旋碼（評估）

quiet 的超音波 profile 使用 rate-1/2 迴旋碼（v27）＋Viterbi 軟解碼。評估：8 bytes 模板封包的 RS 碼字是 14 bytes = 28 個符號；加上 rate-1/2 迴旋碼後變成 56 個符號，封包從 2.4 秒變成約 4.1 秒，超過需求的「3 秒內」。而我們的失敗主因是同步（偵測、header）與多路徑造成的整段衰落，不是隨機的單一符號錯誤，迴旋碼的效益有限。**不實作**；改以不增加封包長度的「軟判決＋抹除」與「重送合併」利用軟資訊。

### 3.6 分段累積（William 提出，經 A/B 改良）

**原版**（William，commit `2098029`）：解碼窗從 0.75 加長到 0.9 個符號，整窗套 Hann 後切成 2 段，各段 Goertzel 功率相加（平方律、非同調）。動機是手機移動穿過駐波節點、訊號相位在符號中途反轉時，整窗同調計算會互相抵銷。

**問題**：拆開測試後發現，原版的進步幾乎都來自「窗加長」，「切段」本身在噪音下是損失——訊號穩定時，兩段功率直接相加比整窗同調少約 3 dB 的積分增益（切 3 段更差：極強 16 → 3/80）。而原本的通道模擬所有反射共用同一個都卜勒，移動時不會產生衰落，所以「切段抵抗相位反轉」的好處根本沒被測到。

**改良**
1. **模擬器加入移動多路徑衰落**（`ChannelOptions.multipathMotion`）：每條反射路徑有隨機入射角 θ，手機移動時反射路徑長度的變化是直達路徑的 cos θ 倍。20 kHz 波長只有 1.7 cm，移動幾公釐直達與反射的相位關係就改變。新增兩種動作：**手持微動**（站著拿手機，±0.05～0.15 m/s、週期 0.3～2 秒的晃動）與**走路**（0.5～1.5 m/s）。舊情境的數字不受影響。
2. **合併方式**（`dsp.ts` `segmentedPower`）：各段改用複數 Goertzel 輸出 y₁、y₂，可以零額外成本同時得到
   - 平方律 |y₁|² + |y₂|²（原版）；
   - 整窗同調 |y₁e^{jωL} + y₂|²；
   - 等增益 (|y₁| + |y₂|)²：「兩段之間相位未知」時的最大似然，訊號穩定時只比同調少約 2.5 dB，相位反轉時不會抵銷；
   - **混合 =（同調 + 等增益）÷ 2**：訊號穩定時等於同調（拿到全部積分增益），相位反轉時同調項歸零、等增益項仍保留一半。
3. **窗長**：0.9 → 1.0 個符號（0.2～1.2，窗尾進入下一個符號的滑音區）。1.1 已測，較差（窄頻干擾 140 → 135、極強 37 → 34）。

**A/B**（`npm run bench -- accum`，同一組種子逐次配對；括號是相對 William 原版「這次成功、原版失敗」／「這次失敗、原版成功」的次數，可看出差異是否只是運氣）

- 整窗同調在噪音與移動衰落下都大幅領先原版，但窄頻干擾掉了 14 次（139 → 125）：干擾音在整窗內是穩定的正弦波，同調積分讓它和訊號一樣得到完整增益。
- 等增益在所有情境都不低於原版，但移動衰落下的進步比同調少。
- **混合兼得兩者**：極強 25 → 43、極強＋手持微動 58 → 95、極強＋走路 7 → 47，窄頻干擾持平（139），任何情境都沒有顯著退步（輸的次數 ≤ 4、贏的次數 ≥ 輸）。**採用為預設**（`RX.accumMetric = 'mix'`、`RX.symWinLenAccum = 1.0`）。

- 「中等」程度的移動情境所有做法都是 150/150，移動本身不是問題；差異出現在「移動＋強噪音」。
- 先前的「每段各自套 Hann」A/B（較差，極強 10 → 7/40）已不保留該選項。

#### 分析

- **速度（ggwave 勝）**：ggwave 每個時刻同時送 6 個音（3 bytes），我們一次只送 1 個音（4 bits），所以 ggwave 的封包短 1.5～2.4 倍。代價是：
  1. **可聽洩漏**：ggwave 的「超音波」從 15 kHz 開始，絕大部分能量在 18 kHz 以下（−1.7 dB），年輕人可以聽到；我們在 16 kHz 以下 −145 dB、18 kHz 以下 −124 dB。這是本專案的最高原則，不可退讓。
  2. **每個音的功率**：峰值振幅固定時，6 個音同時發送，每個音只分到約 1/6 的振幅（−15.6 dB 功率）；我們單音獨占全部功率，所以在「強」噪音下 ggwave 0%、我們 93～97%。
  3. ggwave 的頻率間距 46.875 Hz 對應它自己的 FFT bin，沒有任何頻偏補償；0.5 m/s（19 kHz 偏移 28 Hz，超過半個 bin）就收不到。
- **44.1 kHz 接收（ggwave 敗）**：ggwave 在 44.1 kHz 輸入時成功率大幅下降，推測與其內部重新取樣到 48 kHz、以及 48 → 44.1 線性內插造成高頻衰減有關。許多 Android 手機的麥克風以 44.1 kHz 運作，這在實務上是大問題。
- **結論**：在「人聽不到、車站很吵、乘客會走動、手機取樣率不一」的條件下，我們以每則廣播多 1 秒的代價，換得全面的可靠度。速度上的改善方向見第 6 節。

## 6. 傳輸速度（3.5.3，評估）

目前標準模式：每符號 4 bits、60 ms（8.3 bytes/s 原始速率）；8 bytes 模板封包 = 4（前導碼）+ 4（len、~len）+ 28（14 bytes RS 碼字）= 36 個符號 + 0.26 秒淡入淡出 = 2.42 秒。

| 方向 | 預估封包時間 | 評估 |
|---|---|---|
| 組合式多音 FSK（16 選 2，約 6.9 bits／符號） | 28 → 17 個資料符號，約 1.76 秒（−27%） | 每個音的功率減半（−3 dB）且判定需在 120 種組合中選一；第 0 節顯示「強」噪音下符號 SNR 中位數只有 16.6 dB、「高頻衰減＋中等」10% 分位數 9.3 dB，−3 dB 會讓這兩個情境掉到門檻以下。另外都卜勒追蹤需要「單一主導音」才能估計頻率。**不採用。** |
| 縮短符號（40 ms） | 約 1.70 秒（−30%） | 解碼窗 30 ms，頻率解析度約 33 Hz，Hann 主瓣 ±67 Hz 已超過 50 Hz 間距，相鄰頻道互相洩漏；要加大間距到 75 Hz，頂端會到 20.8 kHz，需求文件的模擬顯示成功率從 25/30 掉到 11/30。**不採用。** |
| 精簡標頭：模板封包固定 8 bytes，以不同的前導碼（例如 A B B A）代表「模板封包、無 len 欄位」 | 省 4 個符號，約 2.18 秒（−10%） | 不影響可靠度，但前導碼種類變多會讓偵測計算量與誤觸發率增加，且失去 header 的長度檢查。可作為下一版的選項。 |

結論：在「不降低第 8 節成功率、不增加可聽洩漏、頻段不超過 20.4 kHz」的限制下，目前的單音 FSK 已接近最佳的取捨；速度的改善空間主要在協定層（精簡標頭）。
