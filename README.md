# 聽見廣播（Hear Broadcast）

> 不需加裝任何硬體：車站現有的廣播喇叭在播放廣播時，同時送出**人耳聽不到的高頻聲波（19.5～20.35 kHz）**，乘客手機的網頁接收並解碼，即時顯示**中文、English、日本語、한국어、台語、客語**字幕——讓聽障者與外國旅客也能「看見」廣播。

大專校院資訊應用服務創新競賽・一般專題類。本版**不使用任何 AI／機器學習／語音辨識**；調變、解調、同步、錯誤更正全部自行實作（純 TypeScript，無 DSP 函式庫依賴）。

| 頁面 | 網址 | 使用者 |
|---|---|---|
| 首頁 | `#/` | 所有人 |
| 乘客端 | `#/rx` | 手機（開始接收 → 字幕） |
| 站務端 | `#/station` | 筆電（選模板 → 播放） |
| 模板管理 | `#/admin` | 管理者 |
| 硬體診斷 | `#/lab` | 安裝人員（掃頻、頻段建議） |

## 1. 核心賣點

- **不打擾聽得到的人（最高原則）**：預設頻段 19.5 kHz 以上；連續相位＋升餘弦滑音＋淡入淡出，16 kHz 以下的洩漏能量約 **−145 dB**、18 kHz 以下約 **−124 dB**。站務端**每次播放前自動做 FFT 洩漏檢查**，超過門檻就拒絕播放。
- **聲音天生帶有位置資訊**：只有聽得到這支喇叭的人才收得到。乘客端以訊號品質自動判斷「目前在第幾月台」，只顯示該月台與全站的廣播——不需要 GPS 或室內定位。
- **完全離線**：模板庫存在手機裡（PWA＋Service Worker），地下車站斷網、緊急事故網路壅塞時照樣能用。封包只送「模板編號＋參數」（8 bytes），字幕在手機端產生。
- **免安裝**：乘客端是網頁，也可以加入主畫面。
- **緊急疏散模式**：緊急廣播觸發全螢幕紅色閃爍、震動、螢幕閱讀器立即朗讀，按「我知道了」才關閉。
- **自動偵測頻段**：不同車站的喇叭特性不同，接收端同時掃描 8 組設定（4 個頻段 × 2 種速度），自動鎖定。
- **邊走邊收（本版最重要的技術創新）**：走路 1.5 m/s 造成的都卜勒偏移（約 87 Hz）比頻道間距（50 Hz）還大，PoC 只要慢慢走就完全收不到（0%）；本版以共用 FFT 的頻偏搜尋＋決策導向追蹤補償，**±0.5～1.5 m/s 與走走停停的情境 97～100%**。

## 3. 數據機與協定規格

### 3.1 調變

- 18 個頻道：`f(i) = f0 + i × 50 Hz`；i = 0 同步音 A、i = 1 同步音 B、i = 2..17 資料音（4 bits）。
- 頻段：**19500 Hz（預設）**、19000、18500、18000 Hz（18 kHz 只能由站務人員手動選，介面會警告）。
- 符號長度：標準 60 ms、穩定 80 ms。8 bytes 模板封包分別約 **2.42 秒、3.14 秒**。
- 連續相位 FSK；每個符號前 15% 以升餘弦曲線滑到新頻率；封包前後各 100 ms 延長音內淡入淡出、30 ms 靜音。
- 預設振幅 0.3（上限 0.8）。

### 3.2 訊框與協定 v2

```
前導碼 A B A B ｜ len ｜ (~len)&0xFF ｜ RS(payload, nsym = 6)      每個位元組 = 2 個符號（高、低 4 bits）
```

| 位元組 | 欄位 | 說明 |
|---|---|---|
| 0 | `(version << 4) \| type` | version = 2；type 1 = 模板、2 = 自由文字 |
| 1 | stationId | 0～255 |
| 2 | platform | 0 = 全站（含緊急），1～15 = 月台 |
| 3 | seq | 0～255 循環，30 秒內去重 |
| 4～7（模板） | packVersion、templateId、p1、p2 | 接收端模板庫較舊時提示更新 |
| 4～（文字） | UTF-8 | 最多 44 bytes |

Reed-Solomon：GF(256)、本原多項式 0x11d、fcr = 0、α = 2、nsym = 6（Berlekamp-Massey、Chien、Forney，修正後重算 syndrome 驗證）。

### 3.3 接收端

1. 兩級 Butterworth 高通（14.5 kHz）去掉人聲與列車噪音。
2. 每個 hop（N/12）偵測前導碼：分數 = `min(rb(t), ra(t−k), rb(t−2k), ra(t−3k))`（不用幾何平均，避免前導碼只收到一半時提早觸發）。
3. 觸發後找峰值、±N/4 以 1 ms 步長精細對齊，解 header，收完封包後判定符號、RS 解碼。
4. 自動偵測：8 組設定共用 16 秒環形緩衝區；第一則成功後鎖定，60 秒沒收到就回到掃描。

### 3.4 本版的優化（原理與數據詳見 [docs/benchmarks.md](docs/benchmarks.md)）

| 優化 | 原理 | 效果（標準模式） |
|---|---|---|
| **都卜勒補償** | 每個 hop 一次 FFT（同符號長度的 4 個頻段共用），±120 Hz 頻偏搜尋；前導碼上估計 α，所有頻道頻率 ×α、符號長度 ÷α；決策導向追蹤（三點拋物線內插） | ±0.5～1.5 m/s：0% → 97～100%；走路（速度變化）：0% → 100% |
| **低 SNR 偵測** | 同步音功率 ÷（背景噪音＋與頻帶最強者的差距），讓訊號只比噪音高幾 dB 也能觸發 | 極強噪音 7% → 17% |
| **軟判決＋抹除** | 信心值 = 最大／第二大功率；RS 失敗時以最不可靠的位元組作為抹除（保留 2 個偵錯餘量）；header 軟判決 | 強噪音 90% → 97%；高頻衰減＋中等（穩定）83% → 100% |
| **重送合併** | 兩次都失敗時，把兩次的頻道功率相加再判定（3 dB＋分集增益），RS 驗證 | 極強噪音：單次 10% → 合併 53%（+43 個百分點） |
| **頻道白化** | 扣除各頻道持續性的背景（設備的窄頻嘯叫） | 窄頻干擾：77% → 97% |

計算量：自動偵測 8 組設定＋頻偏搜尋處理 10 秒音訊，Node 上約 0.5～0.7 秒（比不含頻偏搜尋的 PoC 還快，因為共用 FFT）。

## 6. 展示步驟

**器材**：筆電（站務端）、3.5 mm 一分二音源線（或 USB 音效卡）、兩顆外接喇叭（高音表現好的書架喇叭較佳）、2 支以上手機（乘客端）。

**擺放**：兩顆喇叭分開約 3～5 公尺，各代表一個「月台」；第 1 月台接**左聲道**、第 2 月台接**右聲道**（站務端可改對應）。每支手機靠近其中一顆喇叭。

**步驟**
1. 筆電開啟站務端、手機開啟同一個網址（必須是 HTTPS，例如 GitHub Pages）。
2. **先做掃頻**：手機到「硬體診斷」按「開始接收」→「開始量測」；看到提示後，筆電在「硬體診斷」按「播放 17 → 21 kHz 掃頻」。手機會畫出頻率響應並建議最高可用頻段。
3. 站務端選建議的頻段（建議維持 19.5 kHz），音量從 0.3 開始。**以「收得到的最小音量」為原則**：音量太大時喇叭失真可能產生聽得到的雜音。現場找不同年齡的人聽聽看。
4. 手機到「乘客」按「開始接收」，保持畫面在前景。
5. 站務端選「第 1 月台」播一則、「第 2 月台」播一則：兩支手機各自只顯示自己月台的內容（狀態列顯示「目前判斷您在第 X 月台」）。
6. 按「緊急疏散」：兩支手機都全螢幕紅色閃爍並震動。
7. 拿著手機邊走邊收：狀態列的同步分數與看板仍然正常。
8. 斷網示範：手機開飛航模式後重新整理，乘客端仍可開啟並接收。

## 7. 已知限制

- iPhone 不支援 `navigator.vibrate`，緊急廣播只有畫面與螢幕閱讀器提示（不會報錯）。
- 接收時要停在頁面上：切到其他 App 或鎖定螢幕時，瀏覽器會暫停麥克風（已用 Screen Wake Lock 保持螢幕常亮）。
- 瀏覽器的 TTS（`speechSynthesis`）無法指定輸出聲道；它只是讓展示更像真實車站，不是系統核心。找不到 zh-TW 語音時會略過並提示。
- 不同喇叭、手機的高頻表現差異很大；20 kHz 附近衰減嚴重、現場又很吵時會收不到，要靠提高音量或換用高音較好的喇叭（先用硬體診斷的掃頻確認）。
- 音量開太大時，喇叭失真可能產生聽得到的雜音；數位訊號本身的洩漏檢查抓不到這種情況。請以「收得到的最小音量」為原則，並實際找不同年齡的人聽聽看。
- 兩個月台同時播放會互相干擾，所以站務端以佇列一次只播一則（未來可讓不同月台使用不同頻段）。
- 自由文字不經翻譯，乘客端以原文顯示（未來可接機器翻譯，見第 10 節）。
- Firefox 會把麥克風重新取樣到較低頻率，可能無法接收 19.5 kHz 以上的訊號；建議使用 Chrome、Edge、Safari。

## 8. 頻段選擇的依據

- **為什麼 19.5 kHz 以上**：人耳上限隨年齡下降，成年人多半在 17 kHz 以下，兒童與青少年可達 19～20 kHz；19.5 kHz 以上連年輕人都幾乎聽不到。18 kHz 頻段 18 kHz 以下的洩漏約 −33 dB，可能被部分人聽見，因此只能手動選用並持續顯示警告。
- **為什麼間距 50 Hz**：喇叭與手機麥克風在 20.5 kHz 以上衰減明顯。模擬（兩級 19 kHz 低通、中等噪音）中，75 Hz 間距（頂端 20775 Hz）只有 11/30 成功，50 Hz 間距（頂端 20350 Hz）有 25～26/30。
- **為什麼不用預強調**（在發送端放大高頻頻道）：總音量上限固定時，它會壓低其他頻道，模擬結果反而從 11/30 掉到 1/30。

## 9. 翻譯校對

中文是原文；英、日、韓、台語（漢字）、客語（漢字）由開發者擬稿，**全部標記 `needsReview: true`**，介面會顯示「待校對」。

- 台語請以[教育部臺灣台語常用詞辭典](https://sutian.moe.edu.tw/)校對；客語請以[教育部臺灣客家語常用詞辭典](https://hakkadict.moe.edu.tw/)校對。台語與客語只顯示漢字，不加羅馬拼音。
- 在「模板管理」可勾選「只顯示有待校對翻譯的模板」逐一修改，校對完成後取消該語言的「待校對」。

## 10. 未來路線圖

### 非 AI 擴充
- **後端**：實作 `RemoteRepository`（`src/data/repository.ts` 已有介面），模板庫差異更新、站務端登入與廣播紀錄。
- **原生 App**：以 Capacitor 包裝；只需替換 `src/platform/`（震動、TTS、背景接收）。
- **更多月台**：不同月台使用不同頻段，兩個月台可同時播放而不互相干擾。
- **精簡標頭**：模板封包以專用前導碼省略 len 欄位，封包縮短約 10%（評估見 benchmarks 第 6 節）。
- **延伸場域**：公車到站廣播、醫院與銀行叫號。

### AI 擴充（本版因比賽「一般專題類」限制而不做）

|---|---|---|---|
| `AnnouncementSource` | 模板＋參數、自由文字 | 語音辨識：站務員直接開口廣播，自動轉成文字封包 | 臨時、非制式的廣播不必手動輸入 |
| `Translator` | 模板庫查表 | 機器翻譯自由文字 | 自由文字目前只能顯示原文 |
| `SymbolDetector` | Goertzel 功率＋最大值（軟判決） | 以實際錄到的頻道特徵訓練的神經網路解調器 | 學習特定車站的回音與噪音型態，進一步提升強噪音下的成功率 |
| `ChannelAdvisor` | 掃頻規則（全頻段高於噪音 15 dB） | 依現場噪音自動選頻段與傳輸速度的模型 | 尖峰／離峰、不同月台的噪音差異 |

診斷頁的「匯出頻道特徵」只輸出每個 hop 的 18 頻道功率、同步分數與解碼結果，**不錄任何原始音訊或人聲**，作為未來訓練資料，同時避免隱私疑慮。

## 11. 開發

需求：Node.js 20 以上。

```bash
npm install
```

```bash
npm run dev
```

| 指令 | 說明 |
|---|---|
| `npm run dev` | 開發伺服器（http://localhost:5173） |
| `npm run dev:https` | 區網 HTTPS（自簽憑證），讓同一個 Wi-Fi 的手機也能用麥克風 |
| `npm test` | 所有單元與模擬測試（約 5～8 分鐘） |
| `npm run test:e2e` | Playwright（假麥克風＋離線測試；第一次需 `npx playwright install chromium`） |
| `npm run bench -- <opts\|doppler\|combining\|ggwave\|perf>` | 產生 docs/benchmarks.md 的數據 |
| `npm run lint`、`npm run typecheck`、`npm run format` | 程式品質 |
| `npm run build` | 正式建置（輸出 dist/） |

**手機在本機開發時如何測試**：麥克風需要 HTTPS（localhost 例外）。
- 方法一：`npm run dev:https`，手機開啟終端機顯示的 `https://<電腦 IP>:5173`，在警告頁按「繼續前往」。
- 方法二：直接使用部署後的 GitHub Pages 網址。

### 部署到 GitHub Pages

推送到 `main` 後，GitHub Actions（`.github/workflows/deploy.yml`）會執行 lint、typecheck、單元測試、E2E，通過後以 `VITE_BASE=/<repo 名稱>/` 建置並部署。第一次需要在 repo 的 **Settings → Pages → Source** 選「GitHub Actions」。

### Docker

```bash
docker compose up -d --build
```

開啟 http://localhost:8080。手機要用麥克風必須是 HTTPS：請在前面加上反向代理（例如 Caddy、Nginx＋Let's Encrypt），或使用 GitHub Pages。

### 發布新的模板庫

1. 在「模板管理」編輯（草稿自動存在瀏覽器的 IndexedDB）。
2. 按「匯出」：下載 `template-pack.json`、`stations.json`，`packVersion` 自動加 1。
3. 把兩個檔案放進 `public/data/`，提交並推送；部署後，舊版手機收到新版封包時會提示「模板庫需要更新」。
